Проект реализует сервис поиска визуально похожих товаров одежды по изображению.  
Пользователь загружает фотографию предмета одежды, а система возвращает топ-K наиболее похожих изображений из базы DeepFashion.  
Для извлечения признаков используется предобученная свёрточная нейронная сеть ResNet50, для быстрого поиска — библиотека FAISS.  
Результат — REST API на FastAPI, принимающий изображение и возвращающий ранжированный список схожих товаров.

## 2. Постановка задачи и контекст

### Предметная область и задача

Задача — **визуальный поиск по изображению** (image-to-image retrieval) в сфере электронной коммерции. Потенциальный пользователь: покупатель или стилист, который хочет найти похожую одежду по фотографии (например, сфотографировал вещь в магазине и ищет аналоги онлайн).

Сценарий: пользователь загружает фото через API или веб-интерфейс → сервис возвращает топ-5 визуально похожих изображений из базы с оценками схожести.

### Формулировка задачи в терминах ML

- **Вход:** изображение одежды (JPG/PNG)
- **Выход:** ранжированный список из K ближайших изображений из базы с расстояниями/скорами сходства
- **Тип задачи:** nearest neighbor search в пространстве эмбеддингов (не классификация, не регрессия)
- **Ограничения:** время ответа < 1 сек на CPU; поддержка базы в ~44K изображений

### Целевые метрики качества

- **Recall@K** — доля релевантных результатов в топ-K выдаче (основная метрика)
- **Sanity-check:** изображение, запрошенное само по себе, должно быть на 1-м месте (rank-1 accuracy = 100% при тестировании по базе)
- Дополнительно — визуальная оценка результатов (субъективная релевантность выдачи)

Метрики выбраны потому, что задача — ранжирование, а не классификация; точность topK-выдачи непосредственно отражает качество пользовательского опыта.

## 3. Данные

### Источник

**DeepFashion** — открытый датасет изображений одежды. Используется подмножество, предоставленное в рамках курса (Google Drive, ~6.4 GB).

### Структура данных

- 44 096 изображений в формате JPG
- Все файлы хранятся в плоской структуре в `data/dataset/images/`
- Имена файлов кодируют метаданные: пол (`MEN`/`WOMEN`), категорию (`Denim`, `Shirts`, и др.), ID товара и номер снимка (например, `MEN-Denim-id_00000089-02_7_additional.jpg`)

### Предобработка

При извлечении эмбеддингов применяется детерминированный пайплайн (без аугментаций — для воспроизводимости):

1. Resize до 224×224
2. ToTensor
3. Normalize по статистикам ImageNet (mean=[0.485, 0.456, 0.406], std=[0.229, 0.224, 0.225])

Для потенциального дообучения подготовлен пайплайн аугментаций через `albumentations`: горизонтальный флип, случайный поворот, ColorJitter, GaussianBlur, ShiftScaleRotate.

### EDA

- Датасет однороден: все изображения имеют схожее профессиональное освещение (студийная съёмка)
- Пропущенных файлов при обработке выявлено 0 из 44 096
- Извлечённые эмбеддинги: матрица формы [44096, 2048], float32, ~344 MB в памяти
- L2-нормализация применяется в модели, что позволяет использовать L2-расстояние как приближение косинусного сходства

Основные шаги EDA и подготовки: `notebooks/01_train_embeddings_optimized.ipynb` (ячейки 1–6).

## 4. Модели и подходы

### Baseline

В качестве baseline рассматривался поиск по пиксельным различиям (MSE между изображениями) — очевидно нерабочий подход при разных ракурсах и фонах, но служит нижней границей качества.

### Основной подход — эмбеддинги через предобученную CNN

Использована архитектура **EmbeddingModel** — обёртка над предобученными сетями из torchvision:

| Модель | Размерность эмбеддинга | Параметры | Комментарий |
|--------|----------------------|-----------|-------------|
| ResNet18 | 512 | 11M | Быстрее, меньше памяти |
| **ResNet50** | **2048** | **25M** | **Финальная модель** |
| EfficientNet-B0 | 1280 | 5M | Компактная альтернатива |
| CLIP ViT-B/32 | 512 | 150M | Мультимодальная, требует отдельной установки |

Подход: удалить последний (классификационный) слой сети, взять выход global average pooling, применить L2-нормализацию → получить эмбеддинг размерности D.

### Эксперименты с FAISS-индексом

| Тип индекса | Описание | Время поиска (44K, ~) | Точность |
|-------------|----------|-----------------------|----------|
| **Flat** | Точный перебор | ~100 мс на CPU | 100% |
| IVF (nlist=500, nprobe=5) | Кластерный, приближённый | ~10 мс | ~95–98% |
| HNSW | Графовый, приближённый | ~5 мс | ~95–99% |

В финальной конфигурации (конфиг `project.yaml`) выбран **Flat** — обеспечивает точный поиск при приемлемом времени ответа для датасета в 44K изображений.

## 5. Экспериментальный протокол и результаты

### Протокол

Поскольку задача — unsupervised retrieval без разметки пар «похожих», основная проверка качества:

1. **Sanity-check (rank-1 accuracy):** каждое изображение используется как запрос — оно должно найти само себя на первом месте. Результат: 100% при Flat-индексе.
2. **Визуальная оценка:** ручная проверка релевантности топ-5 результатов для ~20 случайных запросов.
3. **Скорость:** замер latency через `time.perf_counter()` в ячейке построения индекса.

### Сравнение конфигураций

| Конфигурация | Модель | Индекс | Rank-1 Acc | Latency (CPU) | Память индекса |
|---|---|---|---|---|---|
| Baseline | ResNet18 | Flat | 100% | ~60 мс | ~85 MB |
| **Финальная** | **ResNet50** | **Flat** | **100%** | **~110 мс** | **~340 MB** |
| Быстрый вариант | ResNet50 | IVF (nlist=500) | ~97% | ~12 мс | ~340 MB |

### Выбор финальной модели

Выбрана **ResNet50 + Flat index**: даёт наилучшее качество эмбеддингов (2048-мерные признаки против 512 у ResNet18), точный поиск, и время ответа ~110 мс на CPU — приемлемо для демонстрации.  
Trade-off: бо́льший расход памяти (~340 MB) против ResNet18 (~85 MB), но критичным не является.

## 6. Архитектура решения и сервис

### Пайплайн

```
Датасет (JPG)
    │
    ▼
[00_download_dataset.ipynb] — скачивание и распаковка
    │
    ▼
[01_train_embeddings_optimized.ipynb]
    ├─ load_image_paths()    — сканирование директории
    ├─ EmbeddingModel        — ResNet50 без FC-слоя, L2-norm
    ├─ extract_embeddings()  — батчевый инференс → embeddings.npy
    ├─ build_faiss_index()   — построение Flat/IVF/HNSW индекса
    └─ Артефакты: embeddings.npy, metadata.csv, faiss_index.index, run_report.json
    │
    ▼
[src/service/api.py — FastAPI]
    ├─ GET  /health  — статус сервиса
    └─ POST /search  — принимает изображение, возвращает топ-K результатов
```

### API и endpoints

**POST `/search`**
- Принимает: `multipart/form-data` с полями `file` (изображение) и `top_k` (int, по умолчанию 5)
- Возвращает: JSON со списком результатов `[{rank, filename, similarity_score, distance}]`

**GET `/health`**
- Возвращает: `{"status": "ok", "index_size": 44096}`

### Технологический стек

- **PyTorch + torchvision** — извлечение эмбеддингов
- **FAISS** — индексирование и поиск
- **FastAPI + uvicorn** — REST API
- **albumentations** — аугментации
- **gdown** — скачивание датасета с Google Drive
- **pandas, numpy** — работа с метаданными и матрицами

## 7. Наблюдаемость, конфигурация и безопасность

### Логи и наблюдаемость

- Все этапы пайплайна в ноутбуке снабжены `print`-логами с эмодзи-маркерами и `tqdm` прогресс-барами
- После построения индекса сохраняется `artifacts/run_report.json` с параметрами запуска (модель, тип индекса, timestamp, количество векторов) — обеспечивает воспроизводимость
- API логирует время обработки каждого запроса через стандартный `logging`

### Конфигурации

Все ключевые параметры вынесены в `configs/project.yaml`:
- пути к данным и артефактам
- имя модели и устройство (cuda/cpu)
- batch_size и top_k
- тип FAISS-индекса и его параметры (nlist, nprobe)

Смена модели или типа индекса — только правка конфига, код не трогается.

### Безопасность

- Секретов в репозитории нет (нет API-ключей, токенов, паролей)
- Датасет не хранится в репозитории — только скрипт для скачивания
- `.gitignore` включает: `data/`, `artifacts/`, `.venv/`, `*.pyc`, `__pycache__/`

## 8. Ограничения и дальнейшая работа

**Текущие ограничения:**
- Поиск работает только по визуальному сходству; атрибуты (цвет, фасон) не разделены явно
- Нет fine-tuning — используются веса ImageNet, не адаптированные под задачу поиска одежды
- GPU с CUDA capability sm_120 (RTX 5060 Ti) оказался несовместим с текущей версией PyTorch — эмбеддинги извлекались на CPU (медленнее)
- API не имеет авторизации, rate-limiting и пагинации

**При наличии дополнительного времени:**
- Fine-tune модели на triplet/contrastive loss (нужны пары похожих товаров)
- Ансамбль ResNet50 + CLIP: усреднение нормализованных эмбеддингов из двух моделей
- Переход на `faiss-gpu` и актуальную версию PyTorch с поддержкой RTX 50xx
- Добавить фильтрацию по категории (пол, тип одежды) через метаданные в имени файла
- Кеширование (Redis) для повторяющихся запросов
